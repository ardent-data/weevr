# Release Notes — v1.20

**Release date:** October 2026

This release opens weevr's config load to tools that run outside the
engine. The new **`load_resolved()`** loads a thread, weave, or loom
without Spark and hands back everything the engine would run — every
resolved child thread and weave, the load warnings, and the execution
plan — so a CLI or a CI step can check and plan a project the same way
`Context` does.

---

## Inspect a project without Spark

`load_config()` returns the top-level model: a `Weave` holds its thread
*entries*, not the resolved threads, so nothing outside the engine could
build an execution plan from it. `load_resolved()` returns a
`LoadedConfig` carrying the whole resolved tree:

```python
from pathlib import Path

from weevr.config import load_resolved

project = Path("project.weevr")
loaded = load_resolved(project / "nightly.loom", project_root=project)

for weave_name, threads in loaded.resolved_threads.items():
    print(weave_name, list(threads))

for warning in loaded.warnings:
    print(warning)
```

Key details:

+ **Same load as the engine** — `load_config()`, `load_resolved()`, and
  `Context` now run one shared config load, so a `.thread`, `.weave`, or
  `.loom` file resolves the same way through each: params, variables,
  references, the inheritance cascade, `foreach` expansion, and model
  validation of every child.
+ **New on `LoadedConfig`** — `resolved_threads` (each weave's hydrated
  threads, by weave name), `resolved_weaves` (a loom's hydrated weaves),
  and `warnings`. All read-only. `.threads` and `.weaves` still return the
  model's own entries.
+ **Typed files only** — `load_resolved()` accepts `.thread`, `.weave`,
  and `.loom`. With no Fabric context, a `${fabric.*}` reference needs a
  default (`${fabric.workspace_id:-local}`).

See [Loading without running](../guides/config-resolution.md#loading-without-running)
for how the three entry points compare.

## Every plan problem in one pass

`LoadedConfig.validate_plans()` builds each weave's execution plan and
returns one `PlanIssue` per weave that fails — a dependency cycle, two
threads writing the same target without an ordering, a Lookup problem,
or a loom weave that is missing — instead of stopping at the first:

```python
for issue in loaded.validate_plans():
    print(f"{issue.weave_name}: {issue.message}")
```

Each `PlanIssue` carries the weave name, the message, and the original
exception. These are plan-time checks only: nothing reads data. Checks
that need Spark, such as whether a source table exists, stay in
`Context.run(mode="validate")`, which now reports plan problems through
the same method.

## Also included

`load_config()` now matches the engine for typed files:

+ Execution-scope and trace-composition warnings are logged on the
  `weevr.config` logger.
+ Relative file-Source paths come back absolute, resolved against the
  project root (the file's directory when no `project_root` is given).
+ A standalone thread failing on `${param.x}` gets the template-thread
  hint.
+ `qualified_key` is set even without `project_root`.

Fixes shipped since v1.19.0 in patch releases:

+ Inline weaves defined in a loom resolve and run (1.19.3).
+ `incremental_watermark` loads require `watermark_type` (1.19.2).
+ Every config load error names the file it came from; referenced
  threads are validated and their `foreach` steps expanded on load
  (1.19.1).

## Upgrade notes

+ **Absolute file-Source paths from `load_config()`:** code that compares
  or serializes a loaded thread's relative file-Source `path:` now sees
  an absolute path.
+ **New log output from `load_config()`:** load warnings now reach the
  `weevr.config` logger.
+ **Static typing for `load_resolved()`:** it is annotated as returning
  `Any`. Annotate the variable to type-check against `LoadedConfig`:
  `loaded: LoadedConfig = load_resolved(...)`.
+ `.yaml` components and params files load through `load_config()` as
  before. No schema removals and no breaking API changes.

## What's next

The shared config load is an early slice of the v2 loader. The v2
cycle continues with a reshaped telemetry contract and schema-enforced
configuration — see [the roadmap](https://github.com/ardent-data/weevr)
for direction.
